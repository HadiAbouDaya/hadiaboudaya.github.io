# Platform Engineering in the Age of Agentic AI on AWS

A developer asks an agent to add a status filter to an internal inventory API. The agent opens a pull request, asks for a preview environment, and waits. The request times out. It can try again, but did the platform already create the environment? Which revision is running there? Who pays for a second environment, and when does it get cleaned up?

That timeout is a platform engineering problem. A developer using a portal can usually work out what happened by checking the pipeline, asking a colleague, or refreshing the page. An agent needs a reliable way to get the same answer through an interface. As more software work gets delegated, the internal developer platform has to tell callers what they can do, what happened, and what to do next.

I would build that into the same golden path the team already uses. On AWS, the agent can propose a change and collect evidence, while the platform provisions the preview, verifies the artifact and controls its promotion. The following is a reference design for a team running a containerized service on Amazon ECS.

## Give the golden path an API

Start with the developer’s journey. For the inventory team, that means seeing a proposed change running against predictable test data. The platform owns the repeatable work around that journey, including networking, credentials, deployment, health checks and cleanup. A portal, CLI and agent can all use the same contract. The team can package those defaults in a versioned AWS CDK template and offer a small set of parameters developers can understand. [AWS guidance on golden paths and CDK](https://aws.amazon.com/blogs/devops/best-practices-for-scaling-aws-cdk-adoption-within-your-organization/)

I would expose three narrow capabilities to the agent. It can request a preview for a recognized service and reviewed repository context, fetch its status, and retrieve a structured test report. A request names the service and commit. The platform derives the team, permitted environment and budget from authenticated identity and its service catalog. It returns a request ID, an expiry time and a state such as `queued`, `ready`, `failed` or `expired`. The `ready` state includes the resolved artifact digest and a link to the evidence.

The distinction between a commit and a deployed artifact matters. If the pull request changes while the preview is building, the result still belongs to the old commit. The UI and agent response should show that explicitly. The caller supplies a request key up front, so it can retry with that key even if the first response never arrived. A conditional write in DynamoDB can record the key, scoped to the caller and service. Reusing it with the same payload returns the original record. Reusing it with different inputs is an error. That record deduplicates admission. Workers still need a way to reconcile a cloud operation that succeeded before the worker saved its result. [DynamoDB conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html) · [Amazon Builders’ Library on idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

Treat the tool schema and failure responses like any other API. A policy denial should tell an authorized caller which requirement was unmet. A capacity response can tell the caller when to try again. That difference determines whether the agent should ask for a decision or wait. Keep these responses stable across versions so teams can change the portal or switch agent clients without rewriting the delivery path.

## Build once and promote what was reviewed

For this example, I’d run previews in existing nonproduction AWS accounts with synthetic inventory data, short lifetimes and a concurrency limit. AWS Organizations service control policies can set account-level permission ceilings. IAM still grants permissions within those ceilings. Separately, the preview build role should have only the credentials it needs. A pull request can change what the build runs, so its build environment must have neither production secrets nor the ability to assume the production deployment role. [AWS Organizations authorization policies](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_authorization_policies.html)

The delivery pipeline builds a candidate, pushes it to Amazon ECR, and records its digest. The preview and production ECS task definitions refer to that same image by digest when the candidate is eligible for promotion. If the merge produces a different source revision, the pipeline produces and verifies the new candidate before approval. The image digest fixes the container bytes. Task definition, configuration and feature flags can still change behavior, so the release record should identify the target and the relevant configuration revisions too. [Amazon ECS image digest behavior](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-ecs.html)

For the inventory API, the evidence should answer questions a reviewer cares about. Does the existing request still return the same results without the filter? Are unsupported statuses rejected? Does the query preserve tenant isolation? Can the on-call engineer disable the filter, and what should they watch after deployment? The pipeline attaches the real test results. The agent can summarize them and point to the evidence.

An AWS CodePipeline manual approval action can pause production promotion and link to that evidence. In this design, the approver signs off on the commit, digest, target and rollout plan for that execution. The pipeline verifies the approved inputs before promotion and requests fresh approval if they change. The agent can prepare the packet. The authorized service owner makes the release decision, and the deployment role applies it. [CodePipeline manual approval actions](https://docs.aws.amazon.com/codepipeline/latest/userguide/approvals-action-add.html)

## Keep identity and authorization outside the model

There are two ways agents enter this design. A coding agent can use the platform’s existing API from its development environment. An agent the organization operates as a service can use Amazon Bedrock for model inference and Amazon Bedrock AgentCore Runtime for hosting. The delivery path can support both. Teams with an established ECS or EKS runtime can also keep it and adopt selected AgentCore capabilities where those solve an operational problem. [AWS Well-Architected Agentic AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html)

For a centrally hosted developer agent, AgentCore Gateway can expose approved platform operations as MCP tools. With a policy engine attached in `ENFORCE` mode, Cedar policies can authorize calls at the gateway against caller identity and tool inputs. For example, a preview request can be limited to the caller’s permitted service. The platform API also enforces service ownership from trusted identity and catalog records. A tool argument that says `team: inventory` is a request parameter. It has no authority on its own. Credentials and network access must prevent direct backend access from skipping the required checks. [AgentCore policy enforcement](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-getting-started.html)

It helps to draw two arrows when designing this. The first is *caller to gateway*. The second is *gateway to target*. The identities on those arrows can differ. A Lambda target, for example, uses the gateway service role for outbound authorization. For supported targets and identity providers, AgentCore Identity can broker OAuth token exchange for a scoped downstream resource. If authorization depends on the initiating developer, design and verify how the trusted identity reaches the backend. A shared service role tells the target which service called it. The backend needs separate evidence of who is entitled to request the action. [Gateway outbound authorization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html) · [AgentCore Identity token exchange](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-behalf-of-token-exchange.html)

Runtime isolation answers another question. AgentCore Runtime uses dedicated microVMs to isolate sessions, while AWS documents that code inside a microVM can access the runtime execution role. Scope that role and its network access as if the code might attempt whatever the role allows. Use application-level limits on requests, time and model or tool calls to contain a stuck loop. Treat source files, ticket text and tool results as inputs to evaluate. Only the identity and policy checks can authorize a state change. [AgentCore Runtime security guidance](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html)

## Give the workflow a way to finish without the agent

Have the pipeline or an orchestrator own persistent state for work that outlives an agent session. If provisioning and cleanup span several AWS services, a Step Functions Standard workflow can coordinate the steps and wait for a callback where needed. An agent can disconnect while the preview builds and later fetch the authoritative result by ID. Keep callback tokens on the trusted service path. A retry policy belongs to each operation, with a way to check whether a previous attempt already took effect. An orchestrator’s execution guarantees cannot tell you whether a remote system committed a write just before its response was lost. [Step Functions workflow types](https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html) · [Step Functions callback pattern](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html#connect-wait-token)

At rollout, record the deployed digest, keep the on-call owner visible, and decide which signal stops promotion. For ECS, a deployment circuit breaker can catch tasks failing to reach steady state. CloudWatch alarms can catch an application regression such as an increase in API errors. With rollback configured and a previous completed deployment, ECS can restore that service revision. If a later release also writes data or changes a schema, it needs its own recovery plan for those effects. For the filter, a backward-compatible query and a feature flag give the operator a way to disable the new behavior while investigating. [Amazon ECS deployment failure detection and rollback](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-failure-detection.html)

Put the request ID in the platform’s execution records and, where appropriate, in traces. AgentCore and CloudWatch telemetry can help investigate tool calls and latency. Keep a durable release record for who requested the action, the policy decision, the approved inputs, the executing role and the observed result. That record should still answer what happened when a trace was sampled out. Store references to the evidence and redact sensitive values before emitting diagnostics. [AgentCore observability telemetry](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-telemetry.html)

## Measure the work developers can now finish

Start with a single team and its preview path. Watch time to a usable preview, the percentage of requests that succeed without a support ticket, cleanup failures and time waiting for approval. Track change lead time alongside failed deployments and recovery for the same service. Include the cost of retries and reviewer time. If the platform makes it easy to open pull requests but hard to verify them, higher volume just moves the queue to the reviewers. DORA’s research describes AI as amplifying how an organization already works. For this design, I’d test whether the new path reduces waiting across the whole delivery journey. [DORA’s research on AI-assisted software development](https://dora.dev/research/2025/dora-report/) · [DORA delivery metrics](https://dora.dev/guides/dora-metrics/)

Give the agent read access and preview requests first. Before changing the model, prompt or tool set, run the same scenarios again against a test environment. Test a request from the wrong team, a timeout after provisioning, an approval for a stale candidate and a preview whose cleanup fails. AgentCore Evaluations can help assess selected traces for behavior such as tool choice. Assert the hard requirements against platform state directly. Check that the second request reused the same preview, that the stale candidate stayed out of production, and that the cleanup failure reached an owner. Add authority when the team can explain the next action, enforce its boundaries and recover from its failure. [AgentCore on-demand evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-demand-evaluations.html)

The practical test is the developer’s original request. An engineer should be able to hand the inventory change to an agent and come back to a preview of a known revision, credible test evidence and a clear release decision. Achieving that is the platform team’s contribution.
